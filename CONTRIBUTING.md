# Contributing

## Setup

You need JDK 17 or newer; the Gradle wrapper fetches everything else. The
contract suite also needs Node.js (for `npx`).

```sh
./gradlew spotlessApply            # format Java and the build script
./gradlew spotlessCheck build      # what CI runs: format check, compile, unit and README tests, javadoc, generateCheck
./gradlew contractTest             # the client against a Prism mock of the spec (needs npx)
./gradlew sandboxTest              # read-only smoke test against the Sandbox (needs credentials)
./gradlew generate                 # regenerate service, model and param from openapi/sdk-ir.json
./gradlew publishToMavenLocal      # install the jars into ~/.m2 to try them in another project
```

The build compiles with `--release 17`, `-Xlint:all` and `-Werror`.

## Generated and hand-written code

The library is a hand-written core plus a service, model and param layer
generated from the vendored IR (ADR-0001). Layout under
`src/main/java/com/teachmehipaa/`:

| Path                                                              | Origin                                                              |
| ----------------------------------------------------------------- | ------------------------------------------------------------------- |
| `TeachMeHipaaClient.java`                                         | Hand-written, except the service accessors between the markers      |
| `Environment`, `AppInfo`, `RequestOptions`, `FileUpload`, `OAuth`, `Webhook*`, `RequestLog*` | Hand-written                             |
| `core/`                                                           | Hand-written: transport seam, token providers, request pipeline, model bases, `Page`, `EventTail`, binary responses |
| `exception/`                                                      | Hand-written: `TeachMeHipaaException` and its subclasses            |
| `service/`, `model/`, `param/`                                    | Generated by `generator/`; do not edit                              |
| Files in `Generator.HAND_WRITTEN_FILES`                           | Hand-written files inside the generated packages (see below)        |
| `generator/`                                                      | The generator, a build-only source set that never ships in the jar |
| `openapi/`, `OPENAPI_VERSION`                                     | Vendored from the monorepo; do not edit (see `openapi/README.md`)   |

Every generated file starts with a "Generated from openapi/sdk-ir.json by
generator/. Do not edit" banner. To change generated code, change the
generator, or fix the IR upstream in the monorepo's `tooling/sdk-ir` and
re-vendor it. `./gradlew build` runs `generateCheck`, which fails when the
committed output differs from a fresh run of the generator.

A few files in the generated packages are hand-written and listed in
`Generator.HAND_WRITTEN_FILES`, such as `EventService` and `Operation`. They
extend a generated `…Base` class (`EventServiceBase`, `OperationBase`) to add
behaviour: `events().tail`, `waitForCompletion`, export and delivery
results. The generator refuses to overwrite them. A new hand-written method
goes in `HAND_WRITTEN_METHODS` in `GeneratedSurfaceTest`.

## Regenerating from a new IR

1. Rebuild the IR in the monorepo
   (`bun tooling/sdk-ir/bin.ts --spec <spec> --out <dir>`), copy
   `openapi.developer.json`, `sdk-ir.json` and `sdk-ir.schema.json` into
   `openapi/`, and put the IR's `source.release` in `OPENAPI_VERSION`.
2. Run `./gradlew generate`. It validates the IR against its schema, then
   rewrites `service/`, `model/` and `param/` (formatted with
   google-java-format, deterministic) and the accessors in
   `TeachMeHipaaClient`, deleting files the IR no longer produces. An IR
   shape it has no rule for stops it with an error rather than a guess.
3. Run `./gradlew spotlessCheck build`. `GeneratedSurfaceTest` fails if any
   spec operation lacks exactly one public method with the expected name;
   add new operations to its `EXPECTED_METHODS`.
4. Run `./gradlew contractTest`, add a call to `ContractTest` for any new
   resource family, and add a CHANGELOG entry.

## Tests

| Task           | Source set           | What it runs                                                                                     |
| -------------- | -------------------- | ------------------------------------------------------------------------------------------------ |
| `test`         | `src/test`           | Unit tests: the public client with `FakeTransport`, webhook vectors, generated coverage, README |
| `contractTest` | `src/contractTest`   | The client against a Prism mock of `openapi/openapi.developer.json` (needs `npx`)               |
| `sandboxTest`  | `src/sandboxTest`    | Read-only smoke test against the real Sandbox; skipped without credentials                       |

`contractTest` and `sandboxTest` are not part of `check` or `build`, so a
plain build never needs Node or credentials.

Unit tests cross only the seams agreed in the spec: the public client with
`FakeTransport` injected as its `httpTransport`, and `FakeClock` and
`FakeSleeper` for time, the pure webhook functions, and the generated
surface. Take expected values from the spec, the research docs or worked
examples, never from the code under test. No test calls the live API.

### README samples

`ReadmeTest` keeps the README honest. Every `java` block in the README must
follow a `<!-- sample: <id> -->` line. A sample is statements, members
(fields and methods, such as `importRoster(Path)`) or whole classes (the
webhook controller and servlet); the test tells them apart and wraps the
first two in a class.

1. It compiles every sample with `javax.tools` against the library and the
   frameworks the samples use (Spring Web, the servlet API) and nothing
   else, with `-Xlint:all -Werror`. Gradle passes that classpath as
   `-Dreadme.classpath`.
2. It compiles them again with the library's builders
   (`TeachMeHipaaClient.builder()`, `PartnerGrantTokenProvider.builder()`,
   `OAuth.ExchangeCodeParams.builder()`) swapped for `ReadmeHarness`'s,
   which wire them to `FakeTransport`, then runs each one and checks what it
   printed and sent. The webhook controller and servlet get signed
   Deliveries on the exact path they were signed for, and on wrong paths and
   bodies.

A sample that uses `client` without building it gets the Quickstart's
client, bound to `org_acme`. Samples may name `database`, the caller's own
storage, which `ReadmeHarness.Storage` stands in for. The Gradle `test` task
sets the `TMH_*` environment variables the samples read. To add a sample,
tag it and add a check to `CHECKS` in `ReadmeTest`; the test fails if a
tagged sample has none.

### Contract suite

`./gradlew contractTest` starts Prism
(`npx --yes @stoplight/prism-cli@5.16.0 mock openapi/openapi.developer.json`)
on a free port the first time a test asks for it (`PrismExtension`), waits
until it is listening, and stops it, with the process npx starts, after the
last test. `ContractTest` makes one representative call per resource family.
The client uses a `StaticTokenProvider` and an explicit `organizationId`,
since Prism can't mock the form-encoded token endpoint, and its base URL is
the bare host, since Prism serves the spec's paths without `/v1`. Prism
answers a request that breaks the spec with a 4xx, which fails the call, and
`ViolationRecorder`, wrapped around the real transport, fails the test on
any request violation Prism reports in its `sl-violations` header. A harness
test checks that a deliberately invalid request is caught.

Prism serves static responses built from the spec's schemas. `--dynamic` and
`--errors` are off on purpose: Prism's own generated responses break the spec
(static strings ignore `pattern`; dynamic numbers break OpenAPI 3.1
`exclusiveMinimum`), so either flag makes valid SDK requests fail. Response
violations are therefore ignored; the suite still checks that each response
reads into its typed model.

### Sandbox smoke test

```sh
TMH_SANDBOX_CLIENT_ID=cli_… TMH_SANDBOX_CLIENT_SECRET=tmh_cs_… ./gradlew sandboxTest
```

It introspects the token (expecting mode `test`), lists Courses and lists
Learners in the Sandbox Environment. It never writes, and CI never runs it.

## Releasing

Releases go out from `.github/workflows/release.yml`, which runs only when
dispatched by hand. Two locks keep anything from reaching Maven Central by
accident:

1. **The workflow's `publish` input**, unchecked by default. Without it, a
   run checks formatting, builds, runs the unit, README and contract tests,
   runs `publishToMavenLocal` and keeps the jars, sources, javadoc and POM as
   the `maven-local` artifact. It publishes nothing.
2. **`publishGuard` in `gradle.properties`**, committed as `locked`. Every
   task that publishes to a remote repository depends on
   `checkPublishGuard`, which fails unless `publishGuard=unlocked`, the
   version is not a `-SNAPSHOT`, and a signing key is set. So even a
   `publish` run dispatched by mistake fails before it uploads anything.
   `publishToMavenLocal` is never guarded.

With `publish` checked, a second job in the `maven-central` environment
signs the publication and uploads it to the Central Portal through its
OSSRH-compatible staging API (`./gradlew publishMavenPublicationToCentralPortalRepository`),
then hands the deployment to the Portal as `user_managed`, so it waits there
for a last manual "Publish". The job rebuilds from the same commit as the
verify job.

To ship (Nick):

1. On [central.sonatype.com](https://central.sonatype.com), verify the
   `com.teachmehipaa` namespace and generate a Portal user token.
2. Create a GPG key for signing and publish its public key to a keyserver
   (such as `keys.openpgp.org`).
3. In GitHub, create the `maven-central` environment under Settings >
   Environments, with yourself as a required reviewer, and add its secrets:
   `CENTRAL_PORTAL_USERNAME` and `CENTRAL_PORTAL_PASSWORD` (the user token),
   `SIGNING_KEY` (the ASCII-armored private key) and `SIGNING_KEY_PASSWORD`.
4. In one PR: set `publishGuard=unlocked` and `version` (1.0.0 for the first
   release) in `gradle.properties`, move the CHANGELOG's Unreleased entry
   under that version with the date, confirm the POM's developer entry in
   `build.gradle.kts` and the `TODO(Nick)` placeholders in README.md and
   SECURITY.md, and remove the README's pre-release note.
5. After it merges, dispatch **Release** on `main` once without `publish` and
   check the `maven-local` artifact, then again with `publish` checked and
   approve the `maven-central` deployment. Check the deployment on the
   Portal and press Publish.
6. Tag the release commit `v<version>`, create a GitHub release from the
   CHANGELOG entry, and set `publishGuard=locked` and the next
   `-SNAPSHOT` version again.
